# 支付迁移缺口复核（2026-09-15）

## 范围

仅审阅本地 `cloudfunctions/paymentProxy` 与 `cloudrun/payment-api` 源码；未读取运行时机密、未调用微信支付、未访问支付回调或业务数据库。

## 已知发现

1. `paymentProxy` 只将小程序 OpenID 与客户端参数转发给支付容器，未见服务间签名或请求认证。
2. 支付与退款回调在平台公钥相关配置缺失时存在“跳过验签”的分支；新服务不得保留该降级行为。
3. 支付成功回调调用订单云函数失败时，现有代码仍会返回成功响应；这会使平台停止重试，而订单更新只能依赖后续人工或定时补偿。
4. 现有回调直接调用旧订单云函数，未见独立的入站持久化账本。冻结、切库或回调重放期间不能以该路径作为唯一保护措施。

## 迁移前必须具备的替代能力

- 回调入口以原始请求体和完整签名头执行平台验签；缺少平台公钥、序列号不匹配或验签失败均拒绝处理。
- 验签成功的事件先持久化至与业务事实库隔离的入站存储，并以事件唯一键去重；持久化失败必须返回失败以触发支付平台重试。
- 消费者在同一业务事务中写支付状态、库存/积分变更与业务去重记录；成功提交后才标记入站事件已处理。
- 小程序、旧 CloudBase 代理与新 API 之间使用服务间认证；支付金额、OpenID、订单状态均由服务端按已认证用户和订单重新查询。
- 退款需以受 RBAC 保护的后台审批流程发起，不沿用前端可提交的共享管理密钥。

## 结论

支付模块不具备直接迁移或切换条件。应先在隔离环境完成验签、入站持久化、重复回调、数据库提交后故障、冻结期间到达回调和逐笔对账演练；未经负责人确认，不调整支付回调地址或触发真实支付、退款、物流操作。
