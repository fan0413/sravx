# 源库结构与本地迁移覆盖缺口（2026-09-15）

## 实时发现

- 源 MySQL 当前有 30 张业务表，字段总数和表范围已按只读元数据核验。
- 本地 `server/migrations/` 只包含会话、身份、管理员和资料限制等新服务补充表。
- `scripts/mysql/` 只含积分、礼品卡、订单对齐与剪刀规格等局部脚本，不能作为完整业务 schema 的恢复来源。
- 新发现的 `after_sale_service_addresses`、`scissors_after_sales`、`scissors_after_sale_messages` 没有对应的受版本控制目标迁移。

## 影响

目标库不能以本地旧 SQL 直接重建后宣称等同源库。恢复演练和正式迁移都必须基于冻结时从源 MySQL 导出的完整 DDL，再在“原样恢复成功”之后执行独立、编号、可审计的目标补充迁移。

## 后续要求

1. 在负责人确认受控备份位置后，导出源库完整 DDL（含表、索引、外键、触发器、视图、过程、事件、字符集和排序规则）。
2. 将 DDL 导出物保存在受控迁移证据位置，不作为普通应用源码或聊天附件传播。
3. 为新 API 所需的会话、管理员、回调入站等新增结构保留独立 migration；不得在应用运行期自动建表或改列。
4. 对恢复后的目标库运行 schema diff，确认 30 张业务表和新增结构的差异均有批准记录。
