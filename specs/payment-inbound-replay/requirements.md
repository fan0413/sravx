# 支付回调入站与重放 — 需求草案

## 问题与范围

现有支付回调直接调用旧订单云函数，且在订单更新失败时可能确认成功；切换期间无法证明每一笔已接收回调只产生一次业务变化。本功能为新 API 增加“验签后先持久化、后异步消费”的支付与退款回调基础能力。

范围包含微信支付支付成功回调和退款结果回调的入站记录、签名验证接口、幂等消费状态和隔离环境的重放演练。不包含真实支付发起、真实退款、修改微信支付回调地址、生产消费或小程序上线。

## 用户故事

- 作为支付运营人员，我需要每个通过验签的回调都有可审计的接收记录，避免切换期间丢失支付状态。
- 作为后端服务，我需要对重复通知只产生一次有效业务更新。
- 作为迁移负责人，我需要在隔离环境验证回调重放、消费失败和恢复，而不接触真实支付机密或生产订单。

## 验收条件

1. 当支付或退款回调到达时，系统应在验签成功后保存原始请求体、必要签名头的受控表示、事件类型、内容摘要、接收时间和唯一键，再返回成功确认。
2. 当验签配置缺失、验签失败、解密失败或入站记录无法持久化时，系统应返回失败，且不得写入订单、库存、积分或退款状态。
3. 当同一平台事件重复到达时，系统应只保留一个有效入站事件，并返回符合支付平台协议的确认。
4. 当入站事件尚未成功消费时，系统应保留其待处理状态；消费者失败时应记录可重试失败状态，不得把事件标记为已处理。
5. 当消费者对同一事件重复执行时，系统应通过业务唯一键和数据库事务保证订单、库存、积分或退款业务变化至多发生一次。
6. 当迁移冻结启用时，系统应继续接收并持久化已验签事件，但不得消费到源业务库或目标业务库。
7. 当隔离演练重放支付、退款和重复事件时，系统应输出不含个人信息、订单号、回调原文或机密的摘要结果，并证明每个事件的最终处理次数。
8. 系统不得在日志、Git、测试夹具或错误响应中输出支付密钥、回调原文、完整订单号、手机号、地址、OpenID 或解密后的支付内容。

## 已确定约束

- 回调验签不得存在“配置缺失则跳过”的生产降级分支。
- 生产回调入站存储必须与待迁业务事实库隔离；其具体资源形态需在设计阶段确认。
- 未经负责人确认，不修改微信支付回调地址、不导入支付机密、不处理真实回调、不创建真实支付或退款。

## 待负责人确认

1. 入站存储使用独立 MySQL 数据库、独立 schema，还是托管队列/数据库服务？
2. 回调原文、签名头和加密材料的保留期限、加密方式与可访问角色是什么？
3. 支付成功、退款成功、金额/订单不一致、未知订单分别由谁处理和升级？
4. 冻结期间的消费者启停由哪个负责人执行，恢复时以什么水位作为起点？
