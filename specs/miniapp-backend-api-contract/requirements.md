# 小程序后端 API 契约：需求

## 目标

为当前小程序的“系列浏览 → 商品选配 → 购物袋 → 单件结账 → 支付 → 工具绑定与服务”提供统一的 HTTPS API。目录读取可继续采用现有迁移兼容层；价格、库存、型号、颜色、SRAVX Protect、订单和支付必须由目标服务端作为唯一事实源。

## 范围

- 商品目录、商品详情、型号/颜色选配、库存与服务计划报价。
- 本地购物袋的服务端结账校验；首期维持单件结账，不伪装为多商品合并订单。
- 普通订单、微信支付、支付回调、SN 绑定后保障权益激活。
- 管理端的商品型号、颜色和 SRAVX Protect 计划配置。

不在本期范围：生产迁移切换、真实 Protect 定价上线、身份证采集、激光刻字下单、学徒认证审批、多商品合并结账。

## 用户故事

1. 作为用户，我希望商品详情展示可售型号、颜色与可选服务，选择后看到服务端确认的价格与可用性。
2. 作为用户，我希望加入购物袋后，结账时不会因前端缓存的过期价格、库存或服务资格而产生错误订单。
3. 作为运营人员，我希望在管理端配置型号、颜色、服务计划和适用范围，而非修改小程序文案或商品名称。
4. 作为售后人员，我希望通过订单、SKU 和绑定 SN 追溯用户获得的保修与换购权益。

## 验收标准

1. 当小程序请求商品详情时，系统应返回已上架的型号、颜色组合、SKU、可售状态与服务计划入口；不得返回前端自行计算的库存或价格。
2. 当用户请求报价时，系统应仅接受 SKU ID、数量和服务计划报价 ID；系统应校验上架状态、库存、价格、适用范围与优惠资格，并返回带失效时间的报价单。
3. 当用户创建订单时，系统应只接受报价单 ID、地址 ID、优惠券 ID、备注和幂等键；不得接受客户端传入的金额、商品名称、保修期或权益内容。
4. 当微信支付回调到达时，系统应在验签后以唯一业务键幂等更新订单、扣减库存和记录服务计划购买；重复回调不得产生重复业务变更。
5. 当订单对应剪刀完成 SN 绑定并满足计划生效条件时，系统应生成工具保障权益记录；绑定前不得假定保障已生效。
6. 当服务计划未完成业务、法务、定价和条款审核时，系统应不返回可购买服务报价，前端只能展示说明或不展示选购入口。
7. 当管理员更新型号、颜色、服务计划或适用关系时，系统应保留操作审计；普通用户不得访问管理端接口。
